# PR-08: Offline prospect qualification and proposal drafts

**Status:** implemented locally; no remote repository or pull request is available.

**Objective:** turn explicit caller-supplied fit criteria into a consistent qualification result, stored tenant pipeline and reviewable local proposal draft.

**Files changed:** `company_os/sales.py`, `company_os/api.py`, `company_os/agents.py`, `company_os/worker.py`, `tests/test_sales.py`, README, capability/acceptance/plan docs and local test evidence.

**Architecture:** one strict prospect model and pure qualification function serve both the authenticated prospect API and offline sales worker. Up to 20 named boolean criteria produce a match ratio compared without rounding to the supplied threshold (default 0.7). Empty criteria always remain unqualified. Qualified prospects receive a static read-only CI audit proposal with scope, price and terms left for human agreement. Unqualified prospects receive no draft. All criteria remain `CALLER_SUPPLIED_UNVERIFIED`. Tenant-scoped pipeline records include qualification and draft content; standalone sales jobs store independent job evidence and do not synchronize pipeline records.

**Persistence and compatibility:** `POST /v1/prospects` deduplicates normalized domains within the tenant. Identical inputs return the stored record; changed criteria or threshold return 409. `GET /v1/prospects` returns only the caller's tenant records. Legacy records remain unchanged on replay and listing; they are not retroactively rescored or assigned new drafts. The former free-form `qualified` and `qualification` request fields are rejected; callers must supply named boolean criteria.

**Migration impact:** none; uses the existing prospect table and JSON body.

**Security impact:** authentication and writer permissions apply to creation; readers can list only their own tenant. Strict booleans prevent string/integer coercion from changing qualification. Bounded DNS labels and criterion names limit ambiguous inputs. Criteria are supplied as data and grant no customer, repository or outbound authority. The worker gate rejects qualification presented as verified and drafts attached to unqualified output. No network request or external effect is made.

**Automated tests and evidence:** `.venv/Scripts/python.exe -m pytest -q tests` reported 50 passed with one existing Starlette/httpx deprecation warning; Ruff passed and mypy found no issues in 18 source files. Regressions cover threshold/empty-input boundaries, coercion rejection, persistence across application reopen, replay conflicts, tenant isolation, reader denial, legacy records, and API/worker consistency. See `../evidence/local-implementation-tests.md`. Compose was not rerun for this packet.

**Known limitations:** no prospect discovery, independently checked fit criteria, verified contact consent, pipeline editing, outbound adapter, customer negotiation, or accepted sales/revenue evidence. The caller's permission to record a prospect does not establish permission to contact it. Local drafts are unsigned templates requiring human review.

**Acceptance:** qualification is consistent across API and worker; stored records survive application reopen; tenant boundaries apply to listing and creation; drafts exist only for qualified records; all outreach stays disabled.

**Rollback:** revert this packet's API/workflow/evaluation and documentation changes. No schema migration or external cleanup is required. Existing JSON bodies remain readable by the prior API, though the prior free-form creation behavior returns.
